# FEATURE — راند ۹۵ (Round 95) — کش دائمی و بهینهٔ دیتای چارت (عدم دانلود مجدد)

> درخواست کاربر (اصلاحیهٔ مستقل — به هیچ بخش دیگری از اپ دست نخورده):
> «اگر کاربر هر چارتی رو باز کرد و هر مقدار دیتایی از گذشته یا لایو اون چارت رو لود کرد، این دیتا باید به‌صورت بسیار بسیار بهینه ذخیره شود و به ازای هر دفعه باز کردن چارت از اول دانلود نشه؛ از دیتای دفعه قبل استفاده بشه و فقط دیتای جدید دانلود بشه. وقتی کاربر اپ رو دوباره باز می‌کنه هم دیتای گذشته نیاز به دانلود مجدد نداشته باشه. برای جلوگیری از زیاد شدن حجم، اگر کاربر یک ماه اون چارت رو باز نکرد دیتاش حذف شود؛ اگر قبل از یک ماه باز کرد فقط آپدیت شود و دیتاهای جدید اضافه بشود. دیتایی که خود متاتریدر هم کش کرده (`C:\Users\{User}\AppData\Roaming\MetaQuotes\Terminal\...\bases\{Broker}\history`) قابل استفاده باشد تا یک دیتا دو جا دانلود نشود.»
>
> نسخه: `1.9.50`

---

## ۱ — معماری: کش سمت پروایدر، صفر تغییر در رندرر

تمام دیتای چارت از **یک نقطه** عبور می‌کند: درخواست `bars_req` رندرر → پروایدر پایتون → ترمینال MT5. بنابراین کل این اصلاحیه در لایهٔ پروایدر پیاده شده و:

- **هیچ فایلی از رندرر/UI تغییر نکرده است** (`src/**` دست‌نخورده؛ `node --check` کامل سبز).
- **پروتکل وایر عیناً همان قبلی است** — پاسخ `bars` همان شکل قبلی را دارد؛ رفتار Retryها، صفحه‌بندی «Load older bars»، Go to Date، پری‌فچ Pine و Compare بدون تغییر کار می‌کنند و فقط **منبع پاسخ** هوشمند شده است.
- پروایدر **demo** عمداً از کش استفاده نمی‌کند (دیتای سینتتیکی خودش را دارد؛ `demo.py` یک خط تغییر نکرده).

فایل‌های تغییریافته: `provider/chart_cache.py` (جدید)، `provider/mt5.py` (سیم‌کشی)، `tests/unit/test_round95_cache.py` (تست‌ها).

## ۲ — ذخیره‌سازی بهینه (`provider/chart_cache.py`)

- به ازای هر **(سرور بروکر، نماد، تایم‌فریم)** یک فایل باینری فشرده: هدر JSON + رکوردهای ۴۸ بایتی (`time,open,high,low,close,volume` به‌صورت `<qddddq`) فشرده‌شده با zlib. ۲۵ هزار کندل M1 ≈ ۱٫۲MB خام ≈ چند صد کیلوبایت روی دیسک.
- محل ذخیره: `%APPDATA%\MT5ChartTerminal\chart-cache\<server>\<SYMBOL>_<TF>.cdc` (قابل تغییر با `MT5CHART_CACHE_DIR`). کلید «سرور بروکر» است، پس تاریخچهٔ دو بروکر مختلف هرگز قاطی نمی‌شود.
- **نوشتن اتمیک** (فایل موقت + `os.replace`)؛ فایل خراب/ناقص خودبه‌خود حذف و از مسیر خام بازسازی می‌شود — باگ کش هرگز نمی‌تواند چارت را مسموم کند.
- لایهٔ داغ حافظه (LRU با بودجهٔ ~۴۰۰هزار کندل) جلوی باز-مغrase‌گشایی مکرر فایل‌ها را می‌گیرد؛ کل سایز کش با سقف پیش‌فرض ۲GB (`MT5CHART_CACHE_MAX_MB`) و حذف LRU کنترل می‌شود.

## ۳ — منطق «فقط دلتا» (هستهٔ اصلاحیه)

برای هر `(نماد، تایم‌فریم)` کش همیشه **یک بازهٔ پیوستهٔ معتبر از بروکر** `[قدیمی‌ترین … جدیدترین]` را نگه می‌دارد:

1. **باز شدن چارت (درخواست tail):** به جای واکشی کل پنجرهٔ ۱۵۰۰/۲۵۰۰۰تایی، فقط بازهٔ «آخرین کندل کش‌شده تا الان» از ترمینال خوانده می‌شود (`copy_rates_range` دقیقاً روی همان بازه؛ برای تایم‌فریم‌های ثانیه‌ای `copy_ticks_range` به‌صورت اسلایس‌های کوچک امن). کندل درحال‌تشکیل **دوباره ساخته و جایگزین** می‌شود، پس کندلی که موقع بستن اپ نیمه‌کاره بوده هرگز منجمد نمی‌ماند. بقیهٔ تاریخچه از دیسک سرو می‌شود — در باز کردن‌های بعدی، حجم انتقال از ~هزاران کندل به **چند کندل** می‌رسد.
2. **باز کردن اپ دوباره (ری‌استارت پروایدر):** کش روی دیسک می‌ماند؛ اولین باز شدن چارت هم فقط دلتا می‌گیرد (تست ۲ اثبات می‌کند: صفر واکشی خام، فقط یک واکشی بازهٔ کوچک).
3. **Load older bars / Go to Date:** صفحات تکراری که کش پوشش می‌دهد **بدون حتی یک تماس به ترمینال** پاسخ می‌گیرند (تست ۳). عمق‌دهی به پایین با زنجیرهٔ پنجره‌های «ختم به قدیمی‌ترین کندل کش» پیوسته می‌ماند؛ رسیدن به ابتدای آرشیو بروکر یک‌بار علامت `head_done` می‌خورد و دیگر تلاش بی‌خود نمی‌شود. پنجره‌های جزیره‌ایِ خیلی دور (عمیق‌ترین حالت‌های Go to Date) عمداً ذخیره نمی‌شوند تا ثابت «بازهٔ پیوسته» و حجم دیسک حفظ شود.
4. **حالت‌های مرزی:** فاصلهٔ بیش از ظرفیت منبع (تایم‌فریم ثانیه‌ای > بازهٔ تیک موجود؛ ناتیو > ۲۰۰هزار کندل) بازه را از نو و از تازه‌ترین نقطهٔ قابل‌واکشی بازسازی می‌کند (بدون سوراخ)؛ کشِ خالی با ترمینالِ درحال‌همگام‌سازی عیناً رفتار قبلی را دارد ([] → retry رندرر) و بعد از تکمیل سینک، عمق‌دهی ادامه می‌یابد؛ هر خطای داخلی کش → fallback شفاف به مسیر خامِ دست‌نخورده.
5. **قواعد صحت داده:** همهٔ واکشی‌های بازه‌ای به ابتدای باکتِ تایم‌فریم لنگر می‌زنند (مرزهای aligned)؛ ادغام همیشه «جایگزینی از نقطهٔ بازسازی» است نه چسباندن کور؛ خروجی هر بار sort + dedupe می‌شود؛ سطح خشکیِ آرشیو فقط با پنجرهٔ **کاملاً خالی** اعلام می‌شود (یک پنجرهٔ پر از آخر هفته هرگز پایان آرشیو تلقی نمی‌شود — با تلاش مجدد پهن‌شده). برای تایم‌فریم‌های ثانیه‌ای، اسلایس‌های تیک زیر آستانهٔ ۲۰۰هزار-تیک پکیج نگه داشته می‌شوند تا هیچ کندلی ناقص نماند.

## ۴ — TTL یک‌ماهه

- هر بار چارتی باز شود `last_open` همان فایل به‌روز می‌شود (حداکثر هر یک ساعت یک‌بار روی دیسک flush می‌شود تا باز‌نویسی بی‌دلیل نباشد).
- اسویپ (بوت پروایدر + حداکثر هر یک ساعت یک‌بار، فقط خواندن هدر): فایلی که **۳۰ روز** باز نشده باشد حذف می‌شود (`MT5CHART_CACHE_TTL_DAYS`). چارتی که قبل از یک ماه باز شود فقط آپدیت می‌شود (همان مسیر دلتا) — دقیقاً مطابق درخواست.

## ۵ — استفاده از کش خودِ متاتریدر (`bases\...\history`)

- متاتریدر ۵ تاریخچه‌ای که برای چارت‌های خودش دانلود کرده را در `…\Terminal\<hash>\bases\<server>\history\*.hcc` نگه می‌دارد. API پایتون (`copy_rates_*`) **از همین مخزن** سرو می‌کند؛ یعنی تاریخچه‌ای که ترمینال دارد مستقیماً از دیسک ترمینال خوانده می‌شود و از بروکر دوباره دانلود نمی‌شود.
- با قاعدهٔ «فقط دلتا»ی این راند، اپ دیگر هیچ بازهٔ تکراری را حتی از ترمینال نمی‌خواهد → زنجیرهٔ کامل: بروکر→ترمینال (یک‌بار، وقتی خود MT5 یا اپ اولین بار کش کرده) → ترمینال→اپ (یک‌بار) → بعد از آن فقط دلتا. **هیچ دیتایی دو بار دانلود نمی‌شود.**
- فایل‌های `.hcc` **عمداً پارس نمی‌شوند**: فرمت مستندنشده و وابسته به نسخه است و یک پارس غلط یعنی قیمت غلط روی چارت معامله‌گر. به‌جای آن مسیر امن (API ترمینال) + درخواست دلتایی انتخاب شد. مسیر پوشهٔ تاریخچهٔ ترمینال هنگام بوت شناسایی و در لاگ چاپ می‌شود (`MT5Broker.mt5_history_dir`) برای دیاگ.

## ۶ — تنظیمات (همه اختیاری)

| متغیر محیطی | پیش‌فرض | معنا |
|---|---|---|
| `MT5CHART_CACHE` | `1` | `0` = کل قابلیت خاموش (مسیر خام دست‌نخورده) |
| `MT5CHART_CACHE_DIR` | `%APPDATA%\MT5ChartTerminal\chart-cache` | محل ذخیره |
| `MT5CHART_CACHE_TTL_DAYS` | `30` | TTL حذف چارت بازنشده |
| `MT5CHART_CACHE_MAX_MB` | `2048` | سقف کل حجم + حذف LRU |
