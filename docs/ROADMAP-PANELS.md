## ۰) چطور از این سند استفاده کنیم (دستور کار چت جدید)

1. **یک فاز در هر چت.** فازهای بزرگ (مثل فاز ۱۲) به زیرفاز شکسته شده‌اند؛
   هر زیرفاز یک چت.
2. ابتدای چت، این جمله را به مدل بده:
   > «فاز N از `docs/ROADMAP-PANELS.md` را اجرا کن. اول بخش قواعد را بخوان.»
3. مدل باید **قبل از کدنویسی** این‌ها را بگوید: فهرست وظایف همان فاز، فایل‌هایی
   که لمس می‌کند، و گیتی که برای هر وظیفه قرمز/سبز می‌شود.
4. هر وظیفه فقط وقتی «انجام‌شده» است که:
   - رفتار در اپ زنده دیده شود،
   - یک گیت خودکار داشته باشد که **با برگرداندن رفع، قرمز شود**
     (اثبات شکستن — قاعدهٔ ثابت پروژه)،
   - `npm run verify` و `npm run check:e2e` سبز باشند،
   - در `docs/HANDOFF-CURRENT.md` یک خط اضافه شده باشد.
5. آخر چت: commit → push → ریلیز مرحله‌ای → تیک زدن چک‌باکس‌های این فایل در
   همان commit.
6. **قبل از بستن فاز:** `node tests/unit/test_roadmap_consistency.mjs` سبز شود.
   اگر قرمز شد، یعنی یا کد عوض شده یا عددی در این سند کهنه است — دومی را اصلاح
   کن، اولی را در گزارش بنویس.

## ۱) قواعد تثبیت‌شدهٔ پروژه (نقض نکن)

این‌ها از ۳۰۵ راند تجربه استخراج شده‌اند و تکرارشان گران تمام شده است.

### ۱.۱ قواعد کاری
| قاعده | جزئیات |
|---|---|
| گزارش‌ها **فارسی** | همهٔ `docs/*.md` فارسی. کد و کامیت‌ها انگلیسی. |
| اثبات شکستن | هر گیت جدید باید یک بار با برگرداندن رفع، **قرمز** دیده شود. برای گیتِ روی فایلِ موجود: `git stash push -- <files>` → تست → `git stash pop`. برای گیتِ **جدید** (فایل تست تازه، وابسته به کدی که تازه اضافه شده) stash بی‌فایده است — این سه روش: (۱) رفع را در یک کامیت موقت `git revert --no-commit <sha>` کن و بعد `git checkout -- .`؛ (۲) یک assertion کلیدی را کامنت کن و کامیت کن، تست را قرمز ببین، برگردان؛ (۳) اگر گیت روی قابلیت جدید است، `git stash -u` (شامل untracked) و بعد اجرا. **در گزارش همان فاز بنویس کدام روش و چه خروجی‌ای دیدی.** |
| بدون تغییر ظاهری خودسر | هر تغییر رنگ/فاصله/آیکون اول باید تأیید شود. |
| تست فلیک ممنوع | گیتِ ۱-از-۶ قرمز، بدتر از نبودن گیت است. علت را پیدا کن، retry نگذار. |
| کد مرجع است | اگر واقعیت کد با این سند تعارض داشت، **کد درست است**. سند را در همان commit اصلاح کن و در گزارش بنویس. سندِ کهنه بدتر از سندِ نبودن است. |

### ۱.۲ دام‌های فنی (همه یک بار ما را گمراه کرده‌اند)
| دام | واقعیت |
|---|---|

| کندل در حال تشکیل | هر مقایسهٔ عددی باید روی **آخرین کندل بسته (`N-2`)** باشد. |
| اعداد نوسانی | `ta.sma` جمع تجمعی O(1) دارد؛ رانش ~۱ulp. برای بازه‌های بسته از `RANGE_EPS = 1e-9` استفاده کن. |
| پیش‌فرض‌ها | طول‌ها را از **سورس اسکریپت** بخوان، هاردکد نکن (ROC=۹، Momentum=۱۰). |
| HMA | `2*WMA(n/2) - WMA(n)` مجاز است از باند بزند. |
| VWAP | از **ابتدای سشن** انباشته می‌شود، نه ۳۰ کندل. |
| شناسهٔ نمونه | هرگز `Date.now()+random` — از `src/core/instance-id.js`. |

### ۱.۳ محیط ویندوز
- `git push` به stderr می‌نویسد و در `2>&1` خطای کاذب نشان می‌دهد — طبیعی است.
- heredoc (`<<'EOF'`) کار نمی‌کند → متن کامیت را در فایل بنویس و `git commit -F`.
- فایل فارسی را با `-Encoding UTF8` بخوان، وگرنه mojibake می‌شود.
- **پورت‌ها:** هر سوئیت E2E باید یک جفت یکتا بگیرد. بازهٔ آزاد اکنون
  **HTTP 9080–9120** و **WS 8930–8990** است (بیشینهٔ مصرف‌شده: HTTP `9075`
  در `audit_r303_indicator_math.py`، WS `8925` در `e2e_round301_tf_switch.py`).
  `8777` = دمو، `8778` = http پرووایدر. قبل از انتخاب، با
  `node scripts/checks/e2e-ports.mjs` تداخل را چک کن (این ابزار در فاز ۰ ساخته شد).
  توجه: ۲۰+ سوئیت قدیمی پورت مشترک دارند؛ چون سریالی اجرا می‌شوند مشکلی نیست،
  ولی **دو سوئیت هم‌زمان در یک شارد** نباید همان پورت را بگیرند.

### ۱.۴ گیت‌های موجود (نباید قرمز شوند)
```
npm run verify      → 183/183 واحد + mt5 (۲۰ تست) + smoke
npm run check:e2e   → 24/24 سوئیت Playwright
npm run check:release -- --tag vX.Y.Z   → ۱۹/۱۹
npm run check:channel                    → کانال آپدیت ناشناس
```
`scripts/checks/e2e-gate.mjs` فهرست سوئیت‌های E2E است؛ هر گیت جدید باید آنجا
ثبت شود تا واقعاً اجرا شود.

**بودجهٔ زمان گیت (قبل از فاز ۰ حل شود).** هر سوئیت یک سرور استاتیک + provider +
Chromium بالا می‌آورد و `check:e2e` آن‌ها را **سریالی** اجرا می‌کند. ۲۴ سوئیت
امروز روی CI 2-vCPU در بودجهٔ `timeout-minutes: 20` جا می‌شود؛ ۱۳ سوئیت جدید
جا نمی‌شود. پس یکی از این دو باید *قبل* از افزودن سوئیت‌ها انجام شود:

- **گزینهٔ الف (انتخاب‌شده):** `check:e2e` به دو گیت شکسته شود —
  `check:e2e` (سوئیت‌های هر روز، ≤ ۲۴) و `check:e2e:panels` (فازهای ۰–۵).
  CI هر دو را در دو job موازی اجرا می‌کند و `timeout-minutes` هر کدام ۲۰ می‌ماند.
- گزینهٔ ب: شاردبندی داخل `e2e-gate.mjs` با `--shard N/M` و دو job ماتریسی.

سوئیت جدید **فقط** با `--shard`-سازگار بودن (پورت یکتا، بدون state مشترک)
پذیرفته می‌شود. تا این زیرساخت ساخته نشود، هیچ فاز ۰+ شروع نشود.
